# Native compiler vs the interpreter, 2026-09-17

Every package fn in the store was pushed through the x64 compiler, and every one that
compiled was run both ways, compiled and interpreted, on synthesized inputs, with the
results diffed byte for byte. This page is the totals; `2026-09-17d-functions.csv` beside
it has every fn.

## The numbers

    package fns                        5,138
    compile to a native binary         3,242   63%
      of those, provable at all        2,124   (inputs could be synthesized)
      of those, identical output       2,116   99.6%
      differ or crash                     23
    don't compile                      1,901

"Compile" means the compiler emitted an ELF for the fn and everything it calls. "Identical"
means the compiled binary and the interpreter produced the same wire bytes for the same
inputs. The 1,118 compiled-but-unprovable fns take a function or a custom-typed value the
input synthesizer can't build, or are effectful (file, network, database); nothing is
known about their correctness either way yet.

On July's numbers (59% compile, 61% provable-equal, over 3,900 fns): the tree is a third
bigger and the equivalence number is real now rather than a sample.

## What blocks the 1,901

Almost all of it is 372 leaf problems that other fns inherit through their call graph.
By root cause, counting every fn that ultimately hangs off it:

    1,031  a builtin the compiler has no implementation of. The big ones:
             sqliteQuery 275 (effectful; out of scope by design)
             stringToList 80, listIndexedMap 79, jsonSerialize 66, uuidParse 58, jsonParse 57
             listUnique 45, listSort 38, listSortBy 37 (need generic ordering; the compiler
             orders numbers only), dateTimeToString 26
      651  the compiler rejects the program. Top shapes: a lambda whose return type it
             can't infer from an empty list literal (81), a `[a, ...rest]` pattern with a
             non-variable tail (58), a list literal of constructors typed `List<t>` against
             a declared `List<T>` (55), reference-count insertion on a non-variable (22)
       89  effectful builtins whose return type the interpreter/compiler seam can't carry
       65  types the bridge can't lower (generic type aliases, DB, streams)
       65  package values holding a blob or a function

So: ~500 fns are one afternoon of routing builtins the compiler's stdlib could implement,
~300 are effectful and stay out until the seam grows, and ~650 are compiler work in four or
five identifiable shapes.

## The 23 that compile and are wrong

8 differ, 15 crash. Of the 8: one is a case we wrote on purpose (`Int8.shiftLeft 1y 8y`,
interpreter masks the shift, compiler gives 0), one is a clock, and five print nothing at
all from the compiled side on a large synthesized record (I could not reproduce any with
hand-built inputs, so the input synthesizer is a suspect). The 15 crashes are two shapes
(ten exit 1, five SIGSEGV), unexplained. Yesterday this list was 50; the fixes were real
miscompiles (a float stored from the wrong register class, a float store that wrote its own
address under register pressure, a nested pattern that read memory before checking the tag).

## Speed

Not measured meaningfully yet. The CSV has a wall time for one interpreted call and for
the compiled binary's whole run; the compiled figure is ~6 ms of process start for
everything, so the ratio column is noise until the harness loops the body. Allocation is
not measured at all. Both are next.

## How to read the CSV

One row per fn, in seven sections in this order: proven equal; compiles but differs or
crashes; compiles but unprovable; blocked by a callee; blocked by a builtin; blocked by a
type; blocked by the compiler. Within a section, callees come before callers (`depth`).
`blocker` names the thing to fix: for a fn blocked by a callee it names the callee, and
that callee's own row names the builtin, type or compiler error at the bottom of the
chain. `test_args` is what the equivalence run tried; `blocker_detail` is the raw message.
